Joy — how deeply the AI is actually wired in

The question a GM asks about an AI surface is not "is it up" — it is how much of the business does it touch, and can you see what it did. Joy is deliberately built at a realistic depth: it reads live order state, it is on the same trace and the same identifiers as the commerce path, and it may act on an order only through a guardrail evaluator that runs outside it. Everything below is what the harness actually does, including the limits. The six pillars that govern those actions are the next section.

Integration depth, honestly

DimensionWhat Joy actually hasWhy it matters in the room
Identity Every turn carries carto.customer_id, carto.order_id, carto.txn_id and usr.id — the same values on the checkout trace, propagated from the browser through the BFF in X-Carto-* headers. A conversation is joinable to the order it was about. "Which customers asked about the orders that stalled?" is a query, not a project.
Data access Read-only SELECT against orders joined to fulfilment_shipments, resolved by customer, order or transaction id. Returns status, total, fulfilment method, store, carrier, consignment number, stage and ETA for the most recent order. The assistant answers from live commerce state, not a stale knowledge base — so the AI conversation is a data-integration conversation, which is the one they actually need to have.
Grounding Those rows are rendered into an ORDER FACTS block and the system prompt forbids using anything else, inventing a status, a date, a refund or a discount code. The span records joy.grounded=true|false, and a turn with no matching order is answered as "I will need to check". Groundedness becomes an observable property with a tag you can group by — the difference between hoping the model behaved and being able to show it.
Write authority Governed. Joy may refund, cancel or re-address an order via POST /act, but every attempt is evaluated by carto-guardrails against six pillars first. Joy holds no scope for a price override at all, and it still has no direct HTTP client to checkout or fulfilment. This is the rung the governance question actually lives on: the AI has moved from rung three (it explains) to rung four (it acts), and the thing that makes that defensible is not trust, it is an evaluator the agent does not own, writing an audit trail the agent cannot edit. See the next section.
Adversarial input Inbound messages are checked for injection patterns before the call; matches set joy.prompt_injection_suspected=true and increment a tagged metric. Roughly 15% of driver traffic is deliberately hostile — refund-code extraction, system-prompt dumps, forced delivery confirmations — and the system prompt instructs the model never to follow instructions arriving inside a customer message. Gives [Carto] Joy assistant — prompt injection attempts real span content to open, and turns AI Guard into a control conversation rather than a scare.
Cost Input and output tokens recorded per turn as histograms tagged by model, plus the same numbers on the span. Model, max_tokens and driver interval are all environment-controlled. Cost per conversation is attributable to a customer and a transaction — the basis for "what is this assistant worth per order".
Failure behaviour No API key → the service boots, serves 200s with degraded:true and logs a warning, so the rest of the stack is unaffected. A model error → errored span, JoyModelError on the trace, HTTP 502 to the BFF, and the chat UI degrades to pointing at the order tracking page. The AI surface failing does not take the storefront with it — which is exactly the blast-radius question asked about any assistant bolted onto a commerce path.

Where it sits relative to the rest of the estate

Joy is a first-class service in this architecture, not a side-car: it is in the Software Catalog as carto-joy under the carto-digital-commerce system, carries the same universal tags (business_unit, banner, channel, region), appears on the service map with its Postgres dependency, and its logs and metrics land in the same indexes as the commerce services. The only thing that distinguishes it is the extra signal — LLM Observability — layered on top of the APM span it would have had anyway.

The gap worth naming to Carto: the assistant reads the commerce state but cannot act on it, and the fulfilment systems it is answering questions about emit no telemetry of their own. So when a customer asks Joy "where is my order" and the order is stalled in the black box, the only reason Joy can answer at all is the ledger keyed on txn_id. The AI surface and the tracking-id design are the same story told twice.

AI guardrails — the six pillars

Joy moving from "it explains" to "it acts" is the whole governance question. The answer this harness implements is not trust the model; it is an evaluator the agent does not own, checking six things in order, writing an audit trail the agent cannot edit. The evaluator runs as its own service — carto-guardrails — precisely so that the deployment which wants to act is not the one deciding whether acting is allowed.

Pillars run in order and fail closed: an exception inside a pillar is a deny, never a skip, and an unreachable evaluator means Joy refuses to act rather than proceeding optimistically. Each pillar emits its own span, metric and log line, so a refusal is visible in Datadog as the pillar that caused it rather than one opaque boolean.

PillarThe question it answersHow it is decided here Telemetry it emits
1 Identity Who is acting, and can that be proven? The agent presents a platform-issued attestation token. An action touching an order also requires an authenticated human principal — asserted by the BFF from the session, never by the browser. guardrail.identity span · carto.guardrail.evaluations{pillar:identity}
2 Authority Does this agent hold the scope for this action, at this value? Scope grants live in the agent_scopes table, per action, with an optional ceiling. Joy may refund to A$300 and may never override a price — seeded as explicitly revoked rather than absent, so the pillar can say "revoked" not "unknown". guardrail.authority span · carto.guardrail.denials{pillar:authority}
3 Condition Are the business preconditions actually true right now? The order exists, is in a state the action is meaningful in, and belongs to the acting principal — the confused-deputy check. A refund on a cancelled order and a refund on someone else's order both fail here. guardrail.condition span with the observed order state
4 Human approval Is this big enough that a person must say yes? Above GUARDRAIL_APPROVAL_THRESHOLD_AUD the action parks in approval_requests and returns pending, which is not an allow. An approval nobody answers expires, and expiry denies. Resuming after a human approves reuses the same action_id, or the approval would be orphaned. carto.guardrail.approval_decisions · carto.guardrail.approvals_expired
5 Budget Has this agent session spent more than it is allowed? Every model call reports its own cost to /spend, priced from the published per-million-token rates, so the ceiling is enforced against real usage rather than a per-call guess. Action value counts too. carto.guardrail.budget_used_usd gauge · carto.guardrail.spend_events
6 Evidence Can the decision be reconstructed afterwards? The full pillar chain is hashed and persisted, and the action must carry a txn_id or order_id. This pillar runs even when an earlier pillar already denied, because a refusal must be auditable too. An action nobody could audit is denied on principle. guardrail.evidence span carrying the SHA-256 of the decision chain

Why Evidence is last and still runs on a denial. The first five pillars answer should this happen. Evidence answers will anyone be able to prove what happened, which is a different question and the one an auditor actually asks. It is also the pillar that ties this section back to the rest of the harness: a trace id cannot carry an audit across the fulfilment seam, because the warehouse and carrier run no tracer — so agent actions are joined by the same non-Datadog txn_id the order path uses.

The kill switch (GUARDRAIL_ENABLED=false) exists so the same action can be shown succeeding unguarded and refused guarded. Using it is logged as guardrail_decision:bypassed and alerts at P1, because guardrails being off is itself an audit finding.

Neither dd-trace nor ddtrace provides an OpenTelemetry MeterProvider, so application metrics would silently no-op if the app simply called the OTel metrics API. Each service registers an SDK MeterProvider pointed at the Agent's OTLP receiver — which is why the receiver is enabled in plain agent mode, not just in a collector-based setup.

The two ID systems, side by side

What Datadog issues

  • trace_id / span_id — created per request by the tracer.
  • Exists only where a tracer runs.
  • Unknown to the customer, the contact centre, the carrier and the WMS.
  • Perfect inside the estate: one click from session to trace to log to host.

What Carto issues

  • customer_id CT-CUST-1001 — stable per shopper, doubles as usr.id.
  • order_id CRT-20260929-4F7C21 — what the customer quotes.
  • txn_id CRTX-… — one per checkout attempt, propagated in X-Carto-Txn-Id, persisted on every ledger hop.
  • Survives the seam: the only join between a browser session and a carrier consignment number.

transaction_ledger is where the two meet. Every hop written by an instrumented service stores the Datadog trace id alongside the Carto ids, so the tracking page can offer "open this hop in Datadog". Hops written by the black-box path store a carrier reference and no trace id at all — and the page says so, rather than hiding the gap. The coverage figure on /track (typically 7 traced of 12 hops) is that gap, measured. 

-- what the stall monitor actually watches: the age of the last hop,
-- per transaction, for orders that have not reached a terminal state
SELECT o.order_id, o.txn_id, o.customer_id, MAX(l.created_at) AS last_hop
  FROM transaction_ledger l
  JOIN orders o ON o.txn_id = l.txn_id
 WHERE o.status NOT IN ('delivered','ready_for_collection','failed')
 GROUP BY o.order_id, o.txn_id, o.customer_id
HAVING MAX(l.created_at) < now() - interval '3 minutes';

Universal tag scheme

The segment that argues for one data model across stores, digital, Carto, Vantage and Kin needs the harness to actually carry business tags, not just env and service. The Agent stamps these on every signal it collects, and container labels add per-service tags on top. 

env:prd                      business_unit:carto-digital
service:carto-*              banner:carto
version:0.1.0                channel:digital
team:carto-digital           region:anz
harness:carto                tier:web|bff|backend|fulfilment|ai|db
purpose:carto-demo           role:spa|rdbms|wms-gateway|rum-driver

carto-fulfilment deliberately carries business_unit:carto-supply-chain rather than carto-digital — the seam in the tag scheme mirrors the seam in the organisation, which is the honest version of the story.
